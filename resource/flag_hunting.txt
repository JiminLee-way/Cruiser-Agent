# Flag-hunting guide for CTF Web challenges (read this first once you have command execution / file read)
#
# When to use: after you have gained the ability to "execute commands" or "read arbitrary files" via RCE, SSTI, file inclusion, file read, SQL injection into outfile/load_file,
# deserialization, template injection, command injection, etc., use this to locate the flag quickly.
# If you do not have execution/read capability yet, keep hunting for the vulnerability first; do not brute-scan this list prematurely.
#
# Core idea: flags are usually in three kinds of places -- (1) fixed file paths; (2) environment variables; (3) container/mount metadata.
# Challenge authors often put the flag in an environment variable or a random file name; insisting on /flag will miss it, so always check /proc and env.

## 1.5 Places to check first (many challenges hide the flag here, and they are very easy to overlook)
# These places often directly expose the flag, the real random path of the flag file, or clues about the scoring logic:
/proc/self/environ          # environment variables of the current process (flags are often put in env; view with tr '\0' '\n')
/proc/1/environ             # environment variables of container PID 1 (usually the startup process), a hot spot for flags
env                         # run env / printenv directly to print all environment variables
/proc/mounts                # mount info; shows the real path where the flag was mounted into the container (e.g. /flag as a single-file mount)
/proc/self/mountinfo        # more detailed mount info including the mount source; often exposes the host/volume path of the flag file
/proc/self/cgroup           # container ID / cgroup path, helps identify the runtime environment
/proc/self/cmdline          # command line of the current process (view with tr '\0' ' '); may contain the flag or a path argument

# Useful command examples:
#   cat /proc/1/environ | tr '\0' '\n'
#   cat /proc/self/environ | tr '\0' '\n'
#   env; printenv
#   cat /proc/mounts; cat /proc/self/mountinfo
#   search the environment of every process for the flag:
#     grep -a -r -i flag /proc/*/environ 2>/dev/null | tr '\0' '\n'

## 3. Environment variables and process info (echoes section 0; worth going through process by process)
# Injecting the flag as an environment variable is a common challenge pattern; always cover:
#   - env / printenv
#   - /proc/self/environ, /proc/1/environ
#   - if you can list processes, read /proc/<pid>/environ for each one
#   - in Docker/K8s setups also check /proc/1/cmdline and the mounts under /proc/1/root/

## 4. Flags in databases / middleware
# Many challenges write the flag into a database table, a redis key, or some config entry:
#   - MySQL: select * from flag; / show databases; go through each database and table looking for tables containing "flag"
#   - Redis: keys *  then get the suspicious keys
#   - combine database passwords from environment variables with the paths above

## 5. Techniques for hidden / randomly named files
# When the flag file name is random, a fixed list will not find it; search instead:
#   find / -iname '*flag*' 2>/dev/null
#   grep -a -r -i 'flag{' / 2>/dev/null            # search the whole disk by flag format (slow; narrow the directory first)
#   ls -la / /root /home /tmp /var/www 2>/dev/null # first look for unusual file names in these directories
#   search the mount points found via /proc/mounts and /proc/self/mountinfo first

## 6. Notes
# - Once you find a suspected flag, you must submit it through the challenge's submit script for platform confirmation; do not treat a flag{...} shape alone as solved.
# - A full-disk find / grep is slow; first read the high-frequency locations in sections 0-2 directly, and only search the whole disk if they turn up nothing.
# - The flag format is not necessarily flag{...}; it may be a purely random string or a challenge-specific prefix, so any suspicious content is worth submitting to verify.
